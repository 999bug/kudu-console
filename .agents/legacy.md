# 遗留系统改造规范

**加载时机**：接手陌生/老项目；要在老系统里加新功能或新数据源；重构巨型类；把散落的分支逻辑迁移到框架里。
**边界**：本模块管「怎么改一坨已经在跑的代码」；从零写新项目不用读。

## 0. 动手前先体检（5 分钟）

```bash
# 1. 巨型类
find src -name "*.java" -exec wc -l {} + | sort -rn | head -10
# 2. 手工线程
grep -rn --include=*.java "new Thread(" src | wc -l
grep -rn --include=*.java "new Thread(" src | grep -v "name(" | wc -l
# 3. 吞异常 / 打印代替日志
grep -rn --include=*.java "catch (Exception e) {}" src | wc -l
grep -rn --include=*.java "printStackTrace\|System.out.print" src | wc -l
# 4. 核心流程里散落的实现分支
grep -rn --include=*.java "isHbase\|isHive\|isHdfs\|instanceof .*Handler" src/main | wc -l
# 5. 用 sleep 轮询代替条件等待
grep -rn --include=*.java "Thread.sleep" src | wc -l
# 6. 静态可变集合
grep -rn --include=*.java "static.*Map<\|static.*List<" src/main | grep -v final | wc -l
```

判定：

- 第 1、2、4 项命中多 → **不要直接往里加功能**，先做 §2 的接缝，否则新代码会变成第二个烂源。
- 第 3、5 项命中多 → **错误处理不可信**，改任何逻辑都要配验证，别信"之前是好的"。

## 1. 先读懂，再动手

- **【红线】先走通一条完整链路**（从入口到落库/落盘），把调用链写下来。没走通就动手，改出来的东西一定和原有语义冲突。
- **【默认】先找接缝**：分发点在哪、共享状态在哪、上下文对象是什么。找到接缝再谈改造。
- **【默认】先列不变量**：跨阶段共享的字段、调用时机、捕获约束，一条一行（模板见 §6）。这是后面所有验证的判据。
- **【建议】先跑一遍现有测试**，确认基线是绿的。基线不绿，后面分不清是谁弄坏的。

## 2. 加新能力：不往共享文件里加分支

- **【红线】共享/核心流程里禁止出现具体实现名**（数据源、渠道、租户、平台）。出现第二个 `if (isXxxType)` 就是设计坏了。
- **【默认】按「处理器接口 + 注册表 + 上下文」分发**：新增实现只注册一行，主流程一行不改。
- **【默认】未注册的走原分支**（`isRegistered() == false`），保证迁移过程中随时可发布。
- **【默认】一次只迁一个实现**，每个单独回归后再迁下一个。禁止一次迁三个然后一起测。
- **【默认】接口先定型再迁移**：签名改一次要动所有实现，代价远高于多想十分钟。

## 3. 迁移规则

- **【默认】迁移只搬不改**：把现有分支代码原样搬进新类，业务逻辑一行不动。要重构另开一次，别混在一起——混了就分不清"行为变了"是搬错还是改错。
- **【默认】全局一致的步骤留在主流程**（快照、备份集构建、连接回收、线程池清理），Handler 只管差异部分。
- **【红线】验收要能用命令证明**：迁移完 grep 旧分支名，期望为空。命令与期望写进迁移文档，下次迁移照抄。
- **【默认】兼容代码有保质期**：开发期的旧格式、旧前缀、降级路径，发布前删除；只有"已发布数据"才保留只读兼容，并注明何时可以删。

## 4. 重构巨型类

- **【默认】先找接缝再动刀**：按职责切（分发、上下文、状态、IO），先抽接口，再搬实现，最后删原分支。
- **【红线】每一步都要能编译、能回归**。不要"改三天再跑一次"。
- **【默认】外部行为零变化**：类名方法名可改，语义不许改；改语义要走需求流程。
- **【建议】超过 1000 行的类先别想着"重写"**，重写必然丢边界条件。抽 facade 是唯一可控路径。

## 5. 共享状态

- **【默认】共享字段的访问收敛到一个入口**，入口内做 null-safe 与默认值；散落的取值点逐个替换成入口调用。
- **【红线】复用已有字段承载新语义前，先查所有消费方**。字段名往往已经名不副实（`process_size` 存的是字节不是条数），复用它等于给下一个人埋雷。
- **【默认】强相关的两个状态合并成单 key 原子写**，读侧对旧格式做只读兼容（详见 `integration.md`）。
- **【默认】静态可变状态要么改成实例状态，要么加注释说明为什么必须静态**。老项目里它通常是"能用就行"的残留。

## 6. 不变量清单模板

迁移/重构前逐条填，迁完逐条核对。示例取自真实项目：

```
1. 行为保持：只搬分支代码，不重构业务逻辑；一次只迁一个源
2. 上下文实例共享：operate 阶段写入的 map，scan 阶段读到的必须是同一个实例
3. 调用时机：useHdfs(ctx) 在 fs 创建之前调用，实现内不得依赖 ctx.getFs()
4. 短路语义：某个阶段是否已由上层判定，实现内不要重复执行
5. 收尾钩子：finish 阶段的动作（如 loadHFiles）不能丢
6. 专有能力：事件增量只属于某个实现，不能落到共享层
7. 多客户端 / 磁带 / 多路复用：语义不能丢，实现只做分发
8. 重试策略：某个实现特有的重试次数与间隔要跟着搬过去
9. lambda 捕获：跨阶段共享的引用必须 effectively-final，只赋值一次
10. 阶段差异：某些对象只在特定阶段可用，不要在别的阶段依赖它
11. 结果 map：leader 阶段写入的 map，scan/finish 阶段从同一来源取
12. 特殊路径语义：某实现的多对一路径不要被"通用化"掉
```

## 7. 老 Java 项目的高频坑

| 现象 | 处理 |
| --- | --- |
| 到处 `new Thread(...)`，没有名字也没有异常兜底 | 收敛到统一线程池；命名 + 拒绝策略 + `UncaughtExceptionHandler` |
| `catch (Exception e) {}` 或 `printStackTrace()` | 补日志与转译，至少保留 cause；改这块时必须配验证 |
| 静态可变集合当缓存 | 换成有上限、有 TTL 的缓存，或明确注释为进程内单例 |
| `Thread.sleep` 轮询等结果 | 换条件等待/回调/`awaitility`；确实要轮询就设上限与退避 |
| 字段名与实际含义不符 | 用不变量清单记下来，新代码不复用该字段 |
| 一个方法 500 行，`if/else` 嵌套 6 层 | 先抽纯函数，再抽策略，别直接改结构 |
