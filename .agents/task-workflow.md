# 任务工作流：spec → plan → 执行 → 台账

**加载时机**：任务预计跨 3 次会话或 3 天以上；新功能要拆多个子任务；接手别人做到一半的活；用户说「接着上次的做」。
**边界**：本文只管「怎么拆、怎么登记、怎么交接」。改动记录与已知问题三分法见 `discipline.md` 第 7 节，不在这里重复。

## 0. 先判断要不要走完整流程

| 任务规模 | 做法 |
| --- | --- |
| 改一个文件、一次会话能收尾 | 直接做，改前列清单即可 |
| 跨多个模块、方案有分歧 | spec（第 1 节）+ 直接做 |
| 要拆 Task、跨多次会话 | spec + plan + 台账（第 1~4 节） |
| 拆给多个子代理并行 | 上面全走 + 任务书与报告（第 3 节） |

判断标准：**现在中断，下一个会话能不能只靠仓库里的文件接着干？** 答不上来就该建台账。

## 1. spec：先把「不做什么」写下来

存目标项目的 `docs/specs/YYYY-MM-DD-<主题>-design.md`。四段必需：

- **背景与目标**：每条目标都要可验收——能被一条命令或一次点击证实
- **非目标**：明确不做的事。**不写非目标，方案会在实现中慢慢长大**
- **方案对比**：至少两个方案，列优点 / 缺点 / 结论；有分歧就给用户选择题，不要自己替他选
- **状态标注**：用户批准后写「已批准（YYYY-MM-DD，选方案 X）」，后续会话不再重新讨论

```markdown
# <主题> 设计文档

> 日期：YYYY-MM-DD。状态：待批准 | 已批准（选方案 X）。

## 1. 背景与目标
- 目标：<可验收的句子>

## 2. 非目标
- <明确不做的事>

## 3. 方案对比
| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |

## 4. 接口与数据模型
```

## 2. plan：拆到能直接执行的粒度

存目标项目的 `docs/plans/YYYY-MM-DD-<主题>.md`。三条硬要求：

- **Global Constraints 置顶**：把注释语言、提交格式、只读边界、私有数据红线**复制进计划文件**。执行者不用跳读别的文档，也就不会漏
- **每个 Task 写清 Files**：Create / Modify / Test 精确到路径。写「修改相关文件」等于没写
- **Interfaces 标消费方**：`Produces（Task 3 消费）: fn(input): Output`。签名一变，消费方必须同步改

```markdown
# <主题> 实现计划

**Goal:** <一句话>　**Spec:** docs/specs/<xxx>-design.md

## Global Constraints
- 注释中文；日志英文；缺失值 = undefined ≠ 0，UI 显示 —
- 提交前缀 [NF]/[IM] + 中文 Subject；无 AI 署名
- 每个 Task 结束跑 test + lint，全绿才提交

### Task 1: <名称>

**Files:** Create `a.ts` · Modify `b.ts` · Test `a.test.ts`
**Interfaces:** Produces（Task 2 消费）`parse(x): Y`

- [ ] Step 1: 先写失败的测试
- [ ] Step 2: 实现
- [ ] Step 3: 测试转绿 + lint + 提交
```

## 3. 拆给子代理：任务书与报告

一次性派发多个子任务时，每个任务配两份文件（存 `.sdd/<plan-name>/`）：

- **任务书 task-N-brief.md**：写到「逐字转录」级。测试代码给全文，子代理只负责：照抄 → 跑红 → 实现 → 跑绿。只写「加个校验」的任务书，产出必然跑偏
- **报告 task-N-report.md**：必须附**两轮**测试输出。第一轮是预期失败（贴报错原文），第二轮是 N/N 通过

没有两轮输出的报告，既证明不了走了 TDD，也证明不了测试真的会失败——**测不出错的测试等于没有测试**。中途被打断时，在报告末尾写交接说明（见第 4 节）。

## 4. 台账：中断恢复的唯一依据

一份台账，存目标项目的 `docs/PROGRESS.md`；子代理模式额外在 `.sdd/<plan-name>/progress.md` 记任务级状态。

**【红线】开始前登记、每步更新、完成移出。** 只在结束时写「完成」，等于把进度留在会话里，会话一断全丢。

```markdown
# 项目进度

> 维护规则：每完成一个功能先更新本文档再提交代码；进行中的任务标 🔄。

## 0. 进行中任务（中断恢复必读）

| 状态 | 任务 | 进度 | 下一步 |
| --- | --- | --- | --- |
| 🔄 运行中 | <任务名>（来源：用户原话 / issue 号） | T1 已完成，T2 方案待确认 | 等确认后做 T3 |
| ✅ 已提交 | <任务名> | <摘要> + 测试结果 + commit 号 | push / 发布 |

## 1. 已完成归档
<明细多了迁到 docs/archive/，这里只留索引>
```

**交接说明**（换模型 / 换会话时必写）三句话：计划文件在哪、任务书在哪、已完成到哪一步。新会话读这三句就能接手，不用重读代码猜进度。

**小瑕疵记账不阻塞**：发现了但本次不修的问题写一行 `Task N: minor (deferred): <描述>`。留痕比修掉更重要，否则「当时发现了、后来忘了」。

## 5. 收尾顺序

固定顺序，不要跳步：

1. `lint && test && build` 三绿（用 profile 里的命令）
2. 更新台账：任务移到「已提交」，写上 commit 号
3. 版本号 + changelog 头部追加（按 profile 的 `version_scheme`）
4. 提交；`push` 按 `push_policy`
5. push 后确认 CI 绿，再宣称发布完成

## 6. 反模式

| 反模式 | 后果 |
| --- | --- |
| 方案只在对话里聊过，没落文件 | 换会话重议一遍，结论还可能相反 |
| plan 里写「修改相关文件」 | 子代理改错地方，或漏改消费方 |
| 台账只记完成，不记进行中 | 中断后无法定位进度，只能重读代码 |
| 报告没有红→绿两轮输出 | 分不清「真 TDD」和「事后补测试」 |
| 中途改需求不更新 spec | 实现与文档分叉，下一个人照文档改必错 |
