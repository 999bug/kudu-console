# 工程纪律

**加载时机**：准备提交、碰凭据或日志、收尾交付、多会话并行、任何 git 操作之前。

## 1. Git 安全红线

**绝对禁止**（损失是"仓库报废"级别，不是"重来一次"级别）：

- `git stash`（含 `push` / `pop` / `-u`）
- `git reset --hard`
- `git checkout -- <file>`（丢弃工作区改动）
- `git clean`（任何参数）
- `git gc` / `git prune` / `git reflog expire`
- `git filter-branch`（唯一例外：用户当次明确授权，且先做 bundle 备份）
- `git rebase`（含 `-i`）
- 直接改写 `.git/` 内部文件（`refs/`、`index`、`objects/`）
- `git push --force`（历史改写需用户单独授权）

**允许**：`add` / `commit` / `push` / `pull --ff-only` / `status` / `log` / `diff` / `show` / `ls-remote` / `fetch`。

**需要先确认**：放弃工作区改动、清理未跟踪文件、切分支时有未提交改动、发现工作区有别人的未完成改动（此时只读，不要 stash 也不要回退别人的文件）。

## 2. 提交规范

- **【红线】commit message 的格式、类型、单号、粒度一律按 `commit.md`**。本文件不再定义类型表——两处标准必然打架，只留一个权威。
- **【默认】改完即提交，不需要每次询问**；`push` 等明确授权（按 profile 的 `push_policy`）。

与格式无关、只属于 git 操作的纪律：

- **【红线】`git add` 只加具体路径**，不用 `-A` / `.`。
- **【默认】提交前看一眼 `git status`**，确认没有 `.env`、配置、日志、构建产物混进来。
- **【默认】多行 message 用 `git commit -F <file>`**，不要拼多个 `-m`，也不要依赖交互式编辑器（AI / CI 环境会卡住）。
- **【默认】提交后刷新代码索引**：仓库有 `.codegraph/` 时执行 `codegraph sync`，索引落后会让后续的结构查询读到旧代码。仓库已配 `.githooks/post-commit`（`git config core.hooksPath .githooks`）就依赖它，没有就自己跑一次；同步失败只提示，不影响提交结果。
- **【红线】不写 AI 署名**（`Generated with ...`、`Co-authored-by: AI`）。
- **【建议】一个改动一个提交**，不攒到最后一次性提一团。

## 3. 身份与匿名（按 profile 的 type）

**oss（开源）**：

```bash
git config user.name "<匿名用户名>"
git config user.email "<GitHub数字ID>+<用户名>@users.noreply.github.com"
```

- **【红线】不出现真实邮箱**（公司、个人都不行），历史提交里已暴露的清理代价极高。
- **【默认】GitHub 端打开两个开关**：Settings → Emails → "Keep my email addresses private"、"Block command line pushes that expose my email"。
- **【默认】流水线 bot 也用 noreply 身份**（`41898282+github-actions[bot]@users.noreply.github.com`）。

**internal（公司内部）**：用公司全局身份，配置写在 profile 里，不要每次临时指定。

## 4. 不入库清单

| 类别 | 具体 | 泄露后果 |
| --- | --- | --- |
| 凭据 | `.env`、token、私钥、密码 | 直接被利用 |
| 环境信息 | 含内网地址的配置、云端资源 ID | 暴露拓扑 |
| 运行产物 | 日志、数据目录、上传文件、`release/` | 仓库膨胀、日志含业务数据 |
| 构建产物 | `target/`、`dist/`、`static/`、`node_modules/` | 与源码不一致 |
| 本地工具 | IDE 配置、截图目录、会话缓存 | 噪音与隐私 |

- **【默认】新增运行期产物的第一件事：判断它属于哪一层，加进 `.gitignore` / `.dockerignore`**。
- **【红线】不确定的文件先不 add**，问清楚再提。
- **【默认】仓库里已有内网地址时**，不要顺手改（可能是有意的示例）；先报告，等确认。

## 5. 脱敏

- **【红线】凭据只存 Secrets / vault / 本地 `.env`**，不进代码、不进文档、不进对话记录。
- **【默认】文档示例用保留地址**：`192.0.2.x`、`example.com`、`<your-token>`、`<registry-domain>`。
- **【默认】日志与报错截图先脱敏**（主机名、IP、账号、表名里可能带业务信息）。
- **【建议】给个 `LOCAL-ONLY.md`（已 gitignore）承接确实需要记录的敏感标识**，而不是写在 README 里。

## 6. 自测闭环（提交前必做）

按项目实际命令替换，但四步的**结构**不变：

1. **构建**：跑项目自己的构建命令，不用猜。
2. **测试**：跑单测；新增逻辑要有对应用例。
3. **实测**：起服务，走一遍主路径（接口 curl、页面点击）。自测端口避开默认端口，避免和已有实例抢。
4. **回归**：改动涉及的拒绝路径也要验（参数缺失、权限不足、目标不存在、并发冲突）。

- **【红线】没跑通不提交**。跑不通就说明卡在哪、已排除什么。
- **【默认】测试要能分层跑**：开发期专用的慢测试用标签分组（JUnit `@Tag("dev")`、pytest marker）并在打包时排除，不要用 `skipTests` 整体跳过——整体跳过等于没有测试。
- **【默认】UI 改动必须截图**，窄屏 + 宽屏各一张。
- **【默认】破坏性操作必须验"该拒绝时真的拒绝"**，不只是验成功路径。

## 7. 长任务的工程记录

**适用范围**：预计超过 3 天，或会跨 3 次以上会话的任务。短任务不必，但一旦发现要跨会话，立刻开始补。

- **【默认】建一份"改动记录"**：按轮次追加（背景 / 改动 / 测试 / 待办 / 提交号）。它比 commit 完整、比设计文档轻，是复盘和交接的唯一依据。
- **【红线】建一份"已知问题清单"，三分法**：待验证 / 已知限制（设计约束，不是缺陷）/ 已修复归档（带提交号）。**评审提出但不修的问题，必须写理由**，否则下轮会被重复讨论。
- **【默认】多份独立评审 + 逐条源码核实**：结论分"成立 / 部分成立 / 不成立"，不成立的也要留证据。单份评审的误报率不低。
- **【默认】一个评审项一个提交**，禁止把多个修复合成一个提交——出问题无法二分定位。
- **【红线】宣称完成必须列出"真机 / 真实环境验证点"**，并明确哪些没验证。单测全绿不等于可用。
- **【默认】阶段文档有保质期**：正式文档定稿后，把 handoff / progress / 集成记录合并删除，只留一份权威。多份并存必然互相矛盾。

## 8. 收尾

- **【默认】停掉本会话起的进程**，释放端口，确认没有把 jar / 二进制锁住（Windows 下会阻塞下一次构建）。
- **【默认】清掉临时脚本、调试输出、`console.log`、临时截图目录**。
- **【默认】交付说明三段**：改了什么文件 / 验证了什么 / 没验证什么。
- **【默认】改了但没提交时说明原因**（等确认、测试未过、改动不完整）。

## 9. 多会话并行

- **【红线】发现工作区有别人的未提交改动时，只做读操作**，不 stash、不回退、不整体 add。
- **【默认】提交前用 `git status` 确认改动归属**，只提自己的那几个文件。
- **【建议】长任务开始前先 `git status` 记一下基线**，结束时对比，避免把别人的改动卷进来。

## 10. 常见反模式

| 反模式 | 为什么不行 |
| --- | --- |
| "顺手" 重构 + 修 bug 一个提交 | 出问题时无法二分定位 |
| 提交信息写"修改" | 半年后自己都看不懂 |
| 用 `stash` 临时存放改动 | 冲突或误 pop 会丢工作；用分支或 commit |
| 为了跑通 CI 删测试 | 掩盖真实缺陷，下次以更大代价出现 |
| 把 `.env` 改成 `.env.bak` 后提交 | 还是入库了 |
| 直接 `docker cp` 改容器里的文件 | 重建即丢，且与镜像不一致 |
