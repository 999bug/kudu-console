# 提交规范

**加载时机**：写任何 commit message 之前；定分支、合并 MR、打 tag 时。
**来源**：公司《代码提交规范 V2.5》（`CodeCommitGuide.md`）。本文是精简版，执行以原文为准；原文没覆盖的边界按本文处理。

## 1. 格式

```
[TYPE][scope]: subject

- body：为什么改、改了什么
- body：注意事项 / 遗留问题

BREAKING CHANGE: 不兼容点的摘要
Closes #123, #456
```

- **Header 必填，Body / Footer 可选**，三者之间空一行。
- `TYPE` 必选，取第 2 节关键字；`scope` 可选，紧跟在类型后（`[IM][compare]:`），全文只用一个分隔符，不要 `()` 与 `[]` 混用。
- 冒号必须是**英文半角**，冒号后必须**紧跟一个空格**。
- **【红线】message 不能为空**，也不能只写 `Fix`、`Modify`、`update` 这类单词。必须说明目的，能写清实现方法与注意事项就写清。
- **【红线】** ai 写的代码，body 中不要携带 类似下面的信息: `Co-Authored-By: Claude Code <noreply@anthropic.com`>

## 2. 类型

| 类型    | 含义                        | 谁要看     | 必填附加信息                        |
| ----- | ------------------------- | ------- | ----------------------------- |
| `NF`  | 新功能，含性能、稳定性、可用性等非功能改进     | 测试 + 产品 | 禅道任务号 + 测试建议                  |
| `BF`  | Bug 修复                    | 测试 + 产品 | Bugzilla 号 + 风险判断与测试建议（是否需回归） |
| `IM`  | 功能改进：改了公用代码或改动较多，需要回归验证   | 测试 + 产品 | 改动内容与目的 + 回归范围                |
| `SC`  | 引入第三方源码（框架、开源库）           | 测试      | 来源地址 + 版本                     |
| `CU`  | 代码更新：风险可忽略、不需要测试与产品关注     | 都不关注    | 无；合并到正式分支时按实际意义改成 NF/BF/IM    |
| `RF`  | 重构：只改结构、命名、样式，不动功能逻辑，且范围小 | 都不关注    | 无；需要测试介入的重构用 `IM`             |
| `Doc` | 文档提交或更新                   | 了解即可    | 无                             |
| `OT`  | 其他：构建流程、工具配置等非业务代码        | 都不关注    | 无；需要测试关注改用 `IM`               |
| `Tag` | 版本发布，由发布脚本自动提交            | —       | 版本号                           |

判定要点，按顺序问自己三句：

1. 有禅道需求？→ `NF`（有需求的改进一律 `NF`，不用 `IM`）
2. 修的是已记录的 bug？→ `BF`
3. 改了公用代码 / 改动量不小，需要回归？→ `IM`；否则 `RF` / `CU` / `OT` 按性质选

## 3. 单号与测试建议

- **【红线】`NF` / `BF` / `IM` 必须带单号**：`NF` 带禅道任务号，`BF` 带 Bugzilla 号。一处修改同时修多个 bug，就把多个号都写上。
- **【默认】`NF` / `BF` / `IM` 必须给测试建议**：测什么、要不要回归、回归范围。这是给测试同事的输入，不是客套话。
- **【默认】`BF` / `IM` / `NF` 正文写六段**：现象（问题或需求）、根因、修改、影响面（要不要回归、哪些场景会变）、测试（跑了什么、结果如何）、测试建议（哪些要在真机或回归验证）。只写"修复了问题"等于没写；根因写不出来，说明还没定位到，那就别急着提交。
- **开源项目（oss）适配**：没有禅道/Bugzilla 时，单号换成 issue 编号，写在 Footer 的 `Closes #123`；没有 issue 就在 body 里说明动机。类型集不变。

## 4. subject / body / footer

- **subject**：中文优先（`NF` / `IM` / `BF` 对外的必须中文）；动词开头、现在时，不用 `changed` / `changes`；有任务或 bug 时直接用其标题；尽量带上模块或特性名，便于 `git log` 检索。
- **body**：讲动机 + 与上一版相比的改动点；可分多行，格式自由，但同样动词开头、现在时。新特性要写清设计要求、实现原理、注意事项、遗留问题。
- **footer**：
  - 不兼容改动 → `BREAKING CHANGE: <摘要>`，后面补变动描述、理由、迁移方法。
  - 关闭 issue → 单独一行 `Closes #42702`，多个用逗号：`Closes #123, #42569, #42702`。
- **revert**：还原提交时以 `revert: ` 开头，后跟被还原提交的 Header，body 里必须写 `This reverts commit <hash>`。

## 5. 粒度与禁止项

- **【红线】一次提交只做一件事**：一个 Feature、或一个 bug、或一个改进。
- **【红线】禁止把互不相关的改动集中到一次提交**。
- **【红线】禁止把一个问题的修改拆成多次提交**（除了 `CU` 允许的个人分支阶段性提交，合并前必须压缩）。
- **【红线】禁止把 Git 当共享平台**：不为共享代码、不留临时性代码到公共分支。
- **【红线】必须用本人账号提交**，禁止借用他人账号——提交记录是追责与追人的唯一依据。
- **【默认】合并 MR 时勾选压缩提交**，并把标题改成实际意义的 `NF` / `BF` / `IM`。

## 6. 分支

| 分支        | 用途                             | 命名与来源                                   |
| --------- | ------------------------------ | --------------------------------------- |
| `master`  | 项目历史与对外发布                      | 长期存在                                    |
| `develop` | 功能集成分支；其上的 bug 修复分支带 `bugfix/` | `bugfix/<bug号>`，如 `bugfix/7052`         |
| `feature` | 新功能，从 `develop` 拉              | 项目组自定义是否允许直推；合并回 `develop` 需测试报告 + 代码评审 |
| `hotfix`  | 已发布版本的紧急修复，从 `master` 拉        | `hotfix/`；合回 `master` 必须评审              |
| `release` | 对外发布准备，按计划从 `develop` 拉        | 只接收 bugfix 与文档                          |
| `oem`     | 定制功能，不并入 `develop`             | `oem/`，建议从稳定分支拉                         |
| `private` | 个人分支                           | `private/<username>/<模块或需求ID>`          |

- **【默认】合并 bugfix 时勾选"删除源分支"**，保持远端干净。
- **【默认】开源项目（oss）不用这套**：`main` + 短命分支（`feat/xxx`、`fix/xxx`），合回 `main` 用 squash。按 profile 的 `commit_style` 决定。

## 7. Tag 与出包

- **【默认】用 tag 保证代码一致性**：出包人员统一打 tag，以对应分支最新 commit 为准。
- **【默认】tag 由发布脚本产生时，message 用 `Tag` 类型**，内容是版本号。
- **【红线】同一个版本号只打一次 tag**，已发出的 tag 不改不重打。

## 8. 评审（关键代码）

不是每行都 review，但关键代码必须评审。**关键代码**：

1. 内核代码；
2. 模块/进程内的关键流程；
3. 涉及多模块协同的流程；
4. 对性能影响大、被频繁执行的代码；
5. 关键或重要算法。
- **【默认】评审召集人 = 该产品/模块的研发负责人**；邀请需在正式评审前 24 小时发出，说明目的与范围。
- **【默认】评审必须有记录并存档**；研发对意见逐条回复，处理方案与意见一起存档。

## 9. 落地方式（含 AI / 自动化）

- **【红线】禁止用 `git commit -m "一行"` 塞下多段内容**。原文要求进交互界面编辑；**在 AI / CI 等无法交互的环境里，等价做法是把完整 message 写进文件后 `git commit -F <file>`**，不要用多个 `-m` 拼。
- **【默认】提交前先 `git status`**，确认没有 `.env`、配置、日志、构建产物混入。
- **【默认】`git add` 只加具体路径**，不用 `-A` / `.`。
- **【默认】改完即提交，`push` 等明确授权**（按 profile 的 `push_policy`）。

检索用：

```bash
git log --oneline -E --grep '^\[(NF|BF|IM)\]'      # 只看需求与缺陷
git log --oneline -E --grep '^\[(Doc|OT|CU)\]'     # 跳过噪音
```

## 10. 反例

```
✗ update
✗ [BF] 修复问题              # 没有 bug 号、没有现象、没有方法
✗ [NF]: 新增功能、修复 bug、升级依赖    # 三件事挤一起
✗ [IM][compare]: 改了点东西   # 信息量为零，回归范围不明
✓ [IM][compare]: 比对改为按列名配对，兼容列顺序差异
  - 原逻辑按列序号比对，列顺序不同即报差异
  - 改为按列名匹配，DECIMAL 精度与 VARCHAR 长度仍参与比对
  - 需要回归：单表比对、按库比对、按前缀比对三条路径
```
